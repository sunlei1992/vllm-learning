# 10 调度优化测试工作流（草案）

> 目标：把「调度改动」变成**可复现、可归因、能证伪**的实验，而不是只看一次 bench 数字。
> 状态：草案，尚未按此完整实跑；基于实验 B/C/D/E 与 010 的已有资产设计。

## 0. 结论

可行，但建议改三处：

1. **先预演、再实现**：用 `sim_policy.py` / `sim_kv_stress.py` 在不改 vLLM 的前提下验证策略在目标 workload 上有没有信号。调度策略经常只是「重新分配延迟」，预演能提前发现「改了也没用」。
2. **主链路先单实例，RS 后置**：RS 只在优化涉及 P/D 路由/KV 传输时才需要。单引擎内的 FCFS/SRS/chunked prefill/KV 准入，用单实例空跑 + `vllm bench serve` 就够，RS 会引入「假 P/D」和冷启动两个噪声源。
3. **同一镜像 + 开关做 A/B**：尽量把优化实现成 `--scheduling-policy` / `--scheduler-cls` 可选，baseline 和 candidate 跑同一个镜像、同一套 timing，只差一个参数。两个镜像会引入构建差异，且难以排除。

## 1. 先分流：优化属于哪一类

| 优化类型 | 例子 | 主链路 | 不需要 |
|---|---|---|---|
| 单引擎排队/批处理 | FCFS/SRS/priority、chunked prefill、`max_num_seqs`、KV 准入/抢占 | 单实例空跑 + `vllm bench serve` | RS |
| P/D 之间的调度 | P/D 配比、KV 传输、路由派发 | P/D 空跑 + RS（或薄代理） | 单实例 |
| KV 数据面/容量 | layerwise buffer、Mooncake、AscendStore | fake AscendStore / VA 空跑 | RS |

判断方法：如果改的是 `Scheduler.schedule()` 里的排序/准入，选第一行；如果改的是 `kv_transfer_params` / connector / RS pipeline，选第二行；如果改的是 KV 布局/offload，选第三行。

## 2. 五阶段流程

### P0 预演（不改 vLLM）

- 策略类：改 `sim_policy.py` 里的 `Scheduler.waiting` 重排，跑 FCFS / 新策略对比。
- KV 压力类：用 `sim_kv_stress.py` 先确认「什么 workload 会触发抢占」。
- 产出：一张「策略 × 指标」表，回答「这个策略在目标 workload 上是否只是重分配延迟」。
- 通过标准：至少一个目标指标（goodput / 短请求 p99）有可观测改善，且没有不可接受的恶化。否则停止，不必改 vLLM。

### P1 实现 + UT + 调度轨迹回归

- 跑相关 UT（vLLM：`tests/v1/core/test_scheduler.py` 等；VA：`tests/ut/...`）。
- 新增**轨迹级**回归：固定一组请求，断言每步的 `num_scheduled_tokens`、`running/waiting`、抢占次数与预期一致。单纯「跑通」不能防止调度顺序被意外改掉。
- 产出：UT 通过 + 1 个 golden trace 测试。

### P2 设计性能 case

每个 case 必须写清「预期效应」和「证伪条件」，否则跑完只会得到一堆数字。

| 维度 | 建议取值 |
|---|---|
| 请求长度 | 短/长混合；`--random-range-ratio '{"input":0.5,"output":0.5}'` 或自定义 JSONL |
| 到达过程 | 同时到达（`--request-rate inf`）/ 泊松（`--request-rate N`）/ 突发（`--burstiness <1`） |
| 负载水平 | 欠载 / 饱和 / 过载三档 |
| KV 压力 | KV 充足（不抢占）/ KV 紧张（触发抢占）两档 |
| 前缀共享 | 无 / 冷缓存 / 热缓存（ais-bench PrefixCache 造数） |
| 对照 | 一个「优化不应有影响」的 null case（如等长请求） |

### P3 单实例空跑 A/B

关键约束：

- `timing=linear`（或 `table`），**不要用 `zero` 做性能结论**；`zero` 只能验证调度行为。
- `clock=real`（server 模式必须；`virtual` / `fast_forward` 只支持离线 `make_engine`）。
- `--kv-cache-memory-bytes` 按真实硬件 KV 容量设置；注意仿真 block_size 默认 32（GPU 常见 16），token 容量可对齐，但 APC 命中粒度不同。
- **完整负载 warmup 跑一遍丢弃**，不要只靠 `--num-warmups 2`（实验 E：冷启动 TTFT 约 2×）。
- baseline / candidate 交替跑（ABAB…），每组 3–5 次，报告 median 与 min/max。
- 计时跑关闭 `--enable-logging-iteration-details`（或两组都开），避免日志开销污染。

### P4 P/D + RS（仅 P/D 相关优化）

- 先跑 `assets/routeserver-sim/run.sh`，它会校验 pipeline 补丁是否生效（`vllm_ascend_prepare_request` 是否存在）。
- 校验 P 响应真的带 `kv_transfer_params`；日志里 `don't contains [kv_transfer_params]` 警告必须为 0。
- 未打补丁时 D 会重新 prefill：请求全 200、token 全对、TTFT 反而更低——**假 P/D**，不能当性能数据。
- RS 比薄代理多 ~5% TTFT；A/B 两组必须用同一条 proxy 路径。
- 同样要「完整负载 warmup 丢弃」。

### P5 分析与归因

Primary：

- goodput（按 SLO）、p99 TTFT（分请求类别）、`total_token_throughput`。

Secondary：

- `queue_time` p50/p99、`waiting_by_reason`、`num_preemptions`、`iteration_tokens_total`、step 数、prefix cache 命中率。

归因树：

1. 轨迹没变 → 优化没被触发（workload 不匹配 / 代码路径没走到）。
2. 轨迹变了但性能不变 → 调度不是瓶颈（timing model/执行占主导），或只是延迟重分配。
3. queue 高、TTFT 正常 → 准入/排队（KV、并发槽位、优先级）。
4. queue 低、TTFT 高 → prefill（长 prompt、APC 未命中、chunk 太小、prefill 抢占）。
5. ITL 高且 queue 低 → decode 竞争/抢占/重算。
6. preemption 上升 → KV 容量或准入策略问题。

## 3. 防假阳性清单

1. **`timing=zero` 下算力免费**：调度差异可能被放大或消失，不能得出「更快/更慢」。
2. **RS 未打补丁**：假 P/D，看起来更快。
3. **冷启动**：首次压测 TTFT 约 2×，必须整轮 warmup 丢弃。
4. **bench 只看端到端**：不能证明调度决策变了；必须看 step 轨迹/queue time。
5. **只看均值**：策略常只重分配延迟（`sim_policy`：makespan 完全相同，mean TTFT 56.5/90.9/143.0）。
6. **KV 容量给错**：空跑不自动对齐真实 HBM，容量错 → 准入/抢占结论全错。
7. **block_size 不一致**：仿真 32 vs GPU 16，APC 命中率与块数不可直接对比。
8. **bench 客户端与 server 抢 CPU**：Mac Docker Desktop 上尤其明显，尽量分开或固定 CPU。
9. **日志/指标开销不对称**：两组必须同样开关。
10. **workload 顺序/shuffle**：`CustomDataset` 默认 shuffle，APC 场景要用 `--disable-shuffle` 保序。

## 4. 最小 vertical slice（单实例，先跑通再扩）

Case：8 条短（128 in / 32 out）+ 8 条长（1024 in / 128 out），同时到达，`max_num_batched_tokens=512`、`max_num_seqs=8`，KV 给到「有排队但不抢占」。

```bash
# 1) case.jsonl（每行 {"prompt": ..., "output_tokens": ...}）
#    注意 bench 的 sim 请求要带 trace；trace 长度 >= 最大 output_tokens

# 2) server（单实例空跑，linear timing，real clock）
python -m vllm.entrypoints.openai.api_server \
  --model /models/Qwen_Qwen3-0.6B --served-model-name qwen \
  --simulate-forward \
  --simulation-config '{"simulate_forward":true,"timing":"linear","timing_args":{"fixed_us":6200,"prefill_us_per_token":15,"decode_us_per_req":2400,"decode_us_per_kv_token":0.14},"clock":"real"}' \
  --kv-cache-memory-bytes $((2*1024*1024*1024)) \
  --enforce-eager --max-model-len 4096 \
  --enable-per-request-metrics --host 0.0.0.0 --port 8000

# 3) bench（同一镜像，baseline/candidate 只差调度参数）
vllm bench serve --backend openai --endpoint /v1/completions \
  --base-url http://127.0.0.1:8000 --model qwen \
  --tokenizer models/Qwen_Qwen3-0.6B \
  --dataset-name custom --dataset-path cases/mixed.jsonl \
  --custom-output-len -1 --disable-shuffle --skip-chat-template --ignore-eos \
  --num-prompts 16 --request-rate inf --max-concurrency 16 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:500 \
  --extra-body '{"trace_decode_token_ids":[100,101,102,103,104,105,106,107],"return_token_ids":true}' \
  --save-result --result-dir results --label baseline
```

先跑一轮完整负载丢弃，再跑 3 次 baseline + 3 次 candidate（交替），最后比较。

## 5. 产物与判定

建议目录：

```text
results/<exp>/<case>/<variant>/
  bench.json          # vllm bench 结果
  metrics_before.txt  # /metrics 快照
  metrics_after.txt
  steps.jsonl         # --simulation-config log_path（如需轨迹）
  server.log
  env.json            # git sha / image id / timing args / kv bytes / block size
```

判定示例（写死在 case 里）：

- 目标：短请求 p99 queue 下降 ≥30%；goodput 提升 ≥5%。
- 护栏：长请求 p99 TTFT 恶化 ≤10%；总吞吐下降 ≤2%；preemption 不增加。
- 证伪：step 轨迹完全相同 → 优化未触发；轨迹变了但指标不变 → 不是瓶颈。

## 7. 实测：vertical slice（2026-10-31，已跑通）

资产：[`assets/vslice/`](assets/vslice/README.md)，完整结果见 [`RESULTS.md`](assets/vslice/RESULTS.md)。

配置：`sim-int:dry-run`、Qwen3-0.6B（仅 config）、linear timing、real clock、KV 4 GiB、
`max_num_seqs=8`、`max_num_batched_tokens=512`、APC 关闭；8 长（725 token）+ 8 短（65 token），
输出 16 token，长请求排在前面；baseline `fcfs` vs candidate `srs`（按 prompt 长度重排 waiting），每组 2 次。

| 指标 | baseline | candidate | delta |
|---|---:|---:|---:|
| p99 TTFT | 694.96 ms | 706.41 ms | +1.6% |
| p50 TTFT | 390.38 ms | 301.91 ms | -22.7% |
| total token throughput | 5739.04 | 5717.73 | -0.4% |
| request goodput (TTFT≤200ms) | 6.55 | 6.96 | +6.2% |
| SHORT queue p50 | 566.33 ms | 14.88 ms | **-97.4%** |
| LONG queue p50 | 43.87 ms | 531.85 ms | **+1112.4%** |
| SHORT wall p50 | 1113.47 ms | 556.87 ms | -50.0% |
| LONG wall p50 | 641.75 ms | 1124.66 ms | +75.2% |

step 轨迹：213 → 204 步；前 3 步内 short 请求 1 → 2、long 请求 5 → 4。**策略确实生效**。

结论：

- 这是一次**延迟重分配**：短请求 queue p50 降 97%，长请求 queue p50 涨 11 倍，总吞吐不变（-0.4%，2 次运行的噪声内）。
- 聚合 p99 TTFT 反而 +1.6%，只看它会误判；per-class 指标才看得出「谁赢谁输」。
- goodput 上升 6.2%，说明按业务 SLO 统计比吞吐/均值更合理。
- 流水线的三个关键证据都拿到了：同镜像开关、step 轨迹变化、per-class 指标变化。

轨迹已固化成 UT：[`assets/vslice/test_vslice_trace.py`](assets/vslice/test_vslice_trace.py)（`bash assets/vslice/run_trace_test.sh`，3 个用例，约 4s）。它用离线 `Scheduler` + fake KV 复刻同一 case，断言：

| 断言 | FCFS | SRS |
|---|---:|---:|
| steps / total tokens | 42 / 6560 | 42 / 6560 |
| first short step | 16 | 0 |
| first long step | 0 | 16 |
| first 3 步 short / long | 0 / 6 | 24 / 0 |
| preemptions | 0 | 0 |

SRS 第 0 步 8 个 short 吃满 512 预算（`short-7` 只分到 57 token）。golden 值钉在 `sim-int:dry-run`（vLLM 0.31.1rc1）；换调度语义时要显式更新。

本轮没做：3+ 次重复与置信区间、KV 压力/APC case、RS/P/D。candidate 首次启动 158s（Docker/CPU 冷启动波动；baseline 18s），再次说明必须整轮 warmup 丢弃。

## 9. 附：950 2P2D + GLM-5.3 容量估算（util 0.85）

> 仅估算，等真实 `Available KV cache memory` / `GPU KV cache size` 回来校准。
> 假设：GLM-5.3 约 743B 参数；W4 权重 0.5 B/param + 5–10% scales；每卡激活/workspace 6 GiB；
> P = TP8×DP2（EP8），D = TP1×DP16（EP16）；C8 KV 约 46.6 KiB/token（主 MLA + 21 个 full indexer）。

| 项 | P（TP8 rank） | D（TP1 rank） |
|---|---:|---:|
| 每卡权重（5% / 10% scales） | 53.2 / 55.8 GiB | 31.1 / 32.6 GiB |
| 每卡 KV（5% / 10%） | 22.4 / 19.8 GiB | 44.5 / 43.0 GiB |
| 每 engine KV（5% / 10%） | **179 / 159 GiB** | 44.5 / 43.0 GiB |
| `GPU KV cache size`（5% / 10%） | **4.03M / 3.57M tokens** | 1.00M / 0.97M tokens |
| blocks@128（5% / 10%） | 31.5k / 27.9k | 7.8k / 7.6k |
| 128K 请求可容纳（无并发余量） | ~30 / ~26 条 | ~7.7 条 |
| 24 前缀 + 32 并发/rank 需要 | 157.8 GiB | — |
| 24 前缀能装下的余量 | **27.7 / 24.2 个前缀** | — |

结论（util=0.85）：

- **无 prefix affinity**：两个 P rank 都缓存 24 个前缀时，每 rank 需要 `24×5.8 + 32×0.58 = 157.8 GiB`；
  5% scales 下 179 GiB 有余量，10% scales 下 159 GiB **贴着上限**，DP LB 稍偏（如 40/24）就会 thrash。
- **有 DP-aware prefix affinity**：每个 rank 只缓存 12 个前缀，`12×5.8 + 32×0.58 ≈ 88 GiB`，
  即使 10% scales 也有一倍余量；这是这个 case 最大的杠杆。
- **D 侧**：每 rank ~44 GiB，64 并发 / 16 rank = 4 条/rank，约 2 倍余量；D 不要开 APC
  （24 前缀 × 5.8 = 139 GiB > 44 GiB），靠 P 传 KV 或按 prefix 路由。
- **敏感项**：若 indexer 是 78 层都算（53.9 KiB/token），24 前缀 + 并发需要 ~181 GiB，
  在 5% scales 下就已经贴边；真实 indexer 层数/scale 必须确认。
