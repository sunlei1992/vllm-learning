# 实验C：移植 PR #61506（带时间模型与 P/D 分离的仿真器）

> 日期：2026-10-28 ｜ 基础：vLLM `a98247ab`（与 VA main 配对）｜ 镜像 `sim-int:dry-run`
> 结论：**#61506 可以移植并跑通**，4 处冲突、无需重编译；P/D 分离（1P1D/2P1D/1P2D/2P2D）

## 1. 为什么有这个实验

#47922（实验B 的基础）明确不支持：TP/PP/DP、KV transfer（P/D）、LoRA、投机解码、
weight transfer、async scheduling。

社区后续在 RFC **#61305** 里提出了完整仿真器：可插拔时间模型 + 录制 + P/D 分离 + 配置搜索。
对应的实现 PR 是 **#61506**（93 commits，43 files，+6889/−123，open）。

本实验把 #61506 移植到我们本地的基础版本上，验证它能不能用。

## 5. P/D 分离

入口（in-process，两个引擎各跑在自己的虚拟时钟上）：

```python
from vllm.v1.worker.simulated.disaggregated import simulate_disaggregated
from vllm.v1.worker.simulated.offline import TimedRequest

result = simulate_disaggregated(prefill_args, decode_args, requests,
                                num_prefill=2, num_decode=1)
result.summary()          # 与 vllm bench serve 同名的指标
```

内部会自动给两个实例配 **NixlConnector**（`kv_producer` / `kv_consumer`），
并用 `vllm.v1.worker.simulated.kv_nixl` 模拟 NIXL 传输时间（`kv_transfer_timing.load_gbps`）。

### 实测（16 请求、prompt 1024、每 2ms 到达、线性时间模型）

| 配置 | duration | mean TTFT | p99 TTFT | mean TPOT |
| :-- | :-- | :-- | :-- | :-- |
| 1P1D | 0.165s | 90.89 ms | 132.90 ms | 1.00 ms |
| 2P1D | 0.153s | 87.51 ms | 123.15 ms | 1.00 ms |
| 1P2D | 0.184s | 92.81 ms | 146.18 ms | 1.00 ms |
| **2P2D** | **0.148s** | **68.95 ms** | **110.27 ms** | 1.00 ms |

- 加 prefill 实例（2P1D）比加 decode 实例（1P2D）更有效——这个 workload 里 prefill 是瓶颈
- 1P2D 反而略差：decode 不是瓶颈，多一个实例引入的路由/等待没有收益
- TPOT 恒为 1.00ms：时间模型里 decode 每步固定 1000us

> 这些数字**只说明仿真器能反映 P/D 比例的影响**，不代表真实 H200 性能——
> 时间模型系数是我们随手设的（`fixed_us=1000, prefill_us_per_token=10`）。

## 7. 局限（离线驱动）

## 10. 在线模式 P/D

### 10.1 关键前提

`vllm serve` 下开 P/D 必须显式给 `kv_transfer_timing`，否则启动报：

```text
ValueError: Simulated KV transfer needs simulation_config.kv_transfer_timing
```

所以 `--simulation-config` 至少要有：

```json
{"simulate_forward": true, "kv_transfer_timing": {"load_gbps": 10}}
```

### 10.2 两个 server 要能互相访问

prefill 返回的 `kv_transfer_params` 里 `remote_host` 是 `localhost`，
两个容器各自一个网络命名空间 → 直接跑两个容器会连不通。

做法：**同一个容器里起两个 server**，共享 localhost，用 side-channel 端口区分：

```bash
VLLM_NIXL_SIDE_CHANNEL_PORT=5600 ... api_server --port 8000 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer"}'
VLLM_NIXL_SIDE_CHANNEL_PORT=5601 ... api_server --port 8001 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer"}'
```

### 10.3 请求流程（手工扮演 proxy）

```json
// 1. 发给 prefill，max_tokens=1
{"model":"qwen","prompt":"Hello","max_tokens":1,
 "kv_transfer_params":{"do_remote_decode":true,"do_remote_prefill":false}}
```

返回：

```json
"kv_transfer_params": {
  "do_remote_prefill": true, "remote_block_ids": [[1]],
  "remote_engine_id": "8d831634...", "remote_host": "localhost", "remote_port": 5600,
  "transfer_mode": "pull"
}
```

```json
// 2. 带上这些参数发给 decode，正常生成
{"model":"qwen","prompt":"Hello","max_tokens":8,
 "kv_transfer_params": { ...上一步返回的对象... }}
```

### 10.4 实测

| 组合 | prefill | decode | 结果 |
| :-- | :-- | :-- | :-- |
| 纯 vLLM | 200，blocks `[[1]]` | 200，8 个 token | ✅ |
| **vLLM + VA** | 200，blocks `[[1]]` | 200，8 个 token | ✅ |

decode 输出是全 0，因为请求没带 `trace_decode_token_ids`，走 `fallback_token_id=0`——
这是预期行为，不是错误。

脚本：`assets/simulate-forward/pd/online_pd.sh`（纯 vLLM）、`online_pd_va.sh`（VA）。

## 11. 局限（补充）

- 在线模式下 NIXL 仍然是**计时模型**，没有真实传输（`nixl` 库都没装）
- 两个 server 必须同容器/同网络，否则 `remote_host=localhost` 连不上
- 时间模型系数未标定，P/D 比例结论只能看相对趋势
