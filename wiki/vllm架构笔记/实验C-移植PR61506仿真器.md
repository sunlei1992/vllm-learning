## 1. 为什么有这个实验

weight transfer、async scheduling。

对应的实现 PR 是 **#61506**（93 commits，43 files，+6889/−123，open）。

本实验把 #61506 移植到我们本地的基础版本上，验证它能不能用。

## 5. P/D 分离

入口（in-process，两个引擎各跑在自己的虚拟时钟上）：

```python
from vllm.v1.worker.simulated.disaggregated import simulate_disaggregated
from vllm.v1.worker.simulated.offline import TimedRequest

result = simulate_disaggregated(prefill_args, decode_args, requests,
                                num_prefill=2, num_decode=1)
result.summary()          # 与 vllm bench serve 同名的指标
```

内部会自动给两个实例配 **NixlConnector**（`kv_producer` / `kv_consumer`），
并用 `vllm.v1.worker.simulated.kv_nixl` 模拟 NIXL 传输时间（`kv_transfer_timing.load_gbps`）。

### 实测（16 请求、prompt 1024、每 2ms 到达、线性时间模型）

| 配置 | duration | mean TTFT | p99 TTFT | mean TPOT |
| :-- | :-- | :-- | :-- | :-- |
| 1P1D | 0.165s | 90.89 ms | 132.90 ms | 1.00 ms |
| 2P1D | 0.153s | 87.51 ms | 123.15 ms | 1.00 ms |
| 1P2D | 0.184s | 92.81 ms | 146.18 ms | 1.00 ms |
| **2P2D** | **0.148s** | **68.95 ms** | **110.27 ms** | 1.00 ms |

- 加 prefill 实例（2P1D）比加 decode 实例（1P2D）更有效——这个 workload 里 prefill 是瓶颈
- 1P2D 反而略差：decode 不是瓶颈，多一个实例引入的路由/等待没有收益
- TPOT 恒为 1.00ms：时间模型里 decode 每步固定 1000us

> 这些数字**只说明仿真器能反映 P/D 比例的影响**，不代表真实 H200 性能——
> 时间模型系数是我们随手设的（`fixed_us=1000, prefill_us_per_token=10`）。

## 10. 在线模式 P/D

### 10.1 关键前提

`vllm serve` 下开 P/D 必须显式给 `kv_transfer_timing`，否则启动报：

```text
ValueError: Simulated KV transfer needs simulation_config.kv_transfer_timing
```

所以 `--simulation-config` 至少要有：

```json
{"simulate_forward": true, "kv_transfer_timing": {"load_gbps": 10}}
```

### 10.2 两个 server 要能互相访问

prefill 返回的 `kv_transfer_params` 里 `remote_host` 是 `localhost`，
两个容器各自一个网络命名空间 → 直接跑两个容器会连不通。

做法：**同一个容器里起两个 server**，共享 localhost，用 side-channel 端口区分：

```bash
VLLM_NIXL_SIDE_CHANNEL_PORT=5600 ... api_server --port 8000 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer"}'
VLLM_NIXL_SIDE_CHANNEL_PORT=5601 ... api_server --port 8001 --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer"}'
```

### 10.3 请求流程（手工扮演 proxy）

```json
// 1. 发给 prefill，max_tokens=1
{"model":"qwen","prompt":"Hello","max_tokens":1,
 "kv_transfer_params":{"do_remote_decode":true,"do_remote_prefill":false}}
```

返回：

```json
"kv_transfer_params": {
  "do_remote_prefill": true, "remote_block_ids": [[1]],
  "remote_engine_id": "8d831634...", "remote_host": "localhost", "remote_port": 5600,
  "transfer_mode": "pull"
}
```

```json
// 2. 带上这些参数发给 decode，正常生成
{"model":"qwen","prompt":"Hello","max_tokens":8,
 "kv_transfer_params": { ...上一步返回的对象... }}
```

### 10.4 实测

| 组合 | prefill | decode | 结果 |
| :-- | :-- | :-- | :-- |
| 纯 vLLM | 200，blocks `[[1]]` | 200，8 个 token | ✅ |
| **vLLM + VA** | 200，blocks `[[1]]` | 200，8 个 token | ✅ |

decode 输出是全 0，因为请求没带 `trace_decode_token_ids`，走 `fallback_token_id=0`——
这是预期行为，不是错误。

脚本：`assets/simulate-forward/pd/online_pd.sh`（纯 vLLM）、`online_pd_va.sh`（VA）。

## 12. 多轮 APC + 二级缓存仿真（Mooncake 代理实验）

> 目的：AscendStoreConnector（Mooncake）当前不能被空跑加载（见 §13），
> 用 **CPU offloading 仿真**做结构等价的代理：HBM(APC) → 二级缓存（有容量上限、有淘汰）→ 重算。

### 12.1 设置

- 模型 Qwen3-0.6B（`k = 112 KiB/token`）
- HBM 虚拟 KV：1 GiB（≈ 9,360 tokens）
- 8 个会话 × 6 轮，每轮新增 512 tokens（base 1024）
- 线性时间模型：`fixed_us=1000, prefill_us_per_token=10`（即 R = 100k tok/s）
- 二级缓存：`OffloadingConnector` + `CPUOffloadingSpec`，`kv_transfer_timing` 的 `load_gbps/store_gbps`

### 12.2 容量扫描（带宽 50 GB/s）

| 二级容量 | 命中率 | 被驱逐请求 | 未命中 tokens | mean TTFT | p90 TTFT |
| :-- | :-- | :-- | :-- | :-- | :-- |
| 无（仅 HBM） | 49.0% | 31/48 | 43,392 | 19.4 ms | 34.2 ms |
| 1 GiB | 53.7% | 25/48 | 36,992 | 19.1 ms | 34.7 ms |
| 2 GiB | 78.2% | 4/48 | 3,808 | 12.0 ms | 15.1 ms |
| **4 GiB** | **81.1%** | 0 | 0 | **11.1 ms** | **14.6 ms** |
| 8 GiB | 81.1% | 0 | 0 | 11.2 ms | 14.7 ms |
| 16 GiB | 81.1% | 0 | 0 | 11.1 ms | 14.7 ms |

**两个结论**：

1. 容量有**阈值效应**：4 GiB（覆盖 25.6K tokens 工作集）之后饱和，再大没有收益
2. 命中率上限 = `1 − 新增 token 占比` = `1 − 512/(1024+512t)` ≈ **81%**，不是 100%

### 12.3 带宽扫描（二级 8 GiB）

| 带宽 | 命中率 | mean TTFT | p90 TTFT |
| :-- | :-- | :-- | :-- |
| 5 GB/s | 81.1% | 53.1 ms | 137.5 ms |
| 10 GB/s | 81.1% | 21.7 ms | 38.0 ms |
| 25 GB/s | 81.1% | 13.7 ms | 20.3 ms |
| 50 GB/s | 81.1% | 11.0 ms | 14.5 ms |
| 100 GB/s | 81.1% | 9.8 ms | 11.7 ms |
| 无二级（参考） | 49.0% | 19.4 ms | 34.2 ms |

**关键**：命中率一直 81%，但 TTFT 从 53ms 到 9.8ms——**命中率不是收益，带宽才是**。

### 12.4 盈亏平衡点与理论吻合

```
B* = k × R = 112 KiB × 100k tok/s ≈ 11.2 GB/s
```

实测：10 GB/s 时 TTFT（21.7ms）已经和不开二级（19.4ms）持平；
5 GB/s 时反而更差（53.1ms）；25 GB/s 以上才有明显收益。

这和前面推的 `B* = k × R` 完全对上——**低于这个带宽，加载不如重算**。

### 12.5 局限

| 项 | 说明 |
| :-- | :-- |
| 不是 Mooncake | CPU offloading 的语义（DRAM 分块）与 block-key 存储不同 |
| 时间模型未标定 | `R=100k tok/s` 是假设值，真实 NPU 要替换 |
| 无真实网络 | 带宽是标量，不建模拥塞和抖动 |
| block_size | 仿真下为 32，与线上 16/128 有差异 |

# 带宽扫描

## 13. AscendStoreConnector（Mooncake）为什么进不了空跑

实测（VA main + `sim-int:dry-run`）：

```python
kv_transfer_config = {
    "kv_connector": "AscendStoreConnector",
    "kv_role": "kv_producer",
    "kv_connector_extra_config": {"backend": "mooncake"},
}
```

```text
ValueError: Simulated forward does not support the AscendStoreConnector connector.
```

来自 `SimulationConfig._verify_kv_transfer`，白名单只有：

| 允许 | 说明 |
| :-- | :-- |
| `NixlConnector`（pull/push） | P/D，worker 侧替换为计时模型 |
| `OffloadingConnector` + `CPUOffloadingSpec` | 两级缓存，传输只计时 |

`AscendStoreConnector` 需要三样空跑没有的东西：

| 需要 | 空跑现实 |
| :-- | :-- |
| scheduler 侧 `LookupKeyClient` → ZMQ → pool worker | 没有 pool worker |
| Mooncake 客户端 + store 服务 | 容器里没有 `mooncake` |
| `register_kv_caches(kv_caches)` 真实张量 | `kv_caches = []` |

### 13.1 如果要支持，需要做什么

照抄 `kv_nixl.py` 的思路：

1. **假 store**：内存 dict + LRU + 容量，key 用 `request.block_hashes`
2. **connector 子类**：继承 `AscendStoreConnector`，scheduler 侧查假 store，worker 侧 no-op
3. **计时**：命中/写入按 `kv_transfer_timing` 计时
4. **放行**：把新类加进白名单

估计 1–2 天。在此之前，用 §12 的 CPU offloading 代理。
## 14. Fake AscendStoreConnector：实现与结果

### 14.1 做了什么

新增 `SimulatedAscendStoreConnector`（VA 仓库，分支 `local/simulated-ascend-store`）：

| 侧 | 行为 |
| :-- | :-- |
| scheduler | **真实语义**：按 `request.block_hashes` 做连续前缀查找、容量受限 LRU、淘汰 |
| store | 内存 dict，容量 = `store_gb`；block 字节 = `page_size_bytes × 层数` |
| worker | 全部 no-op（不注册张量、不搬数据） |

配套的 vLLM 侧改动（移植树）：

1. `SimulationConfig._verify_kv_transfer` 放行 `SimulatedAscendStoreConnector`
2. `simulated_kv_connector` 识别它并挂一个 `_NoTransfers`

### 14.2 实测：容量扫描（8 会话 × 6 轮，HBM 1 GiB）

| store 容量 | 命中率 | 被驱逐请求 | 未命中 tokens | mean TTFT |
| :-- | :-- | :-- | :-- | :-- |
| 无（仅 HBM） | 49.0% | 31/48 | 43,392 | 19.4 ms |
| 0.5 GiB | 49.0% | 31/48 | 43,392 | 19.8 ms |
| 1 GiB | 49.0% | 31/48 | 43,392 | 19.8 ms |
| 2 GiB | 66.3% | 13/48 | 19,968 | 14.5 ms |
| **4 GiB** | **81.1%** | 0 | 0 | **7.9 ms** |

- 阈值在 **2~4 GiB**（工作集约 2.8 GiB）
- 命中率上限仍是 **81.1% = 1 − 新增 token 占比**

### 14.3 和 CPU offloading 代理的对比

| 容量 | fake AscendStore | CPU offloading |
| :-- | :-- | :-- |
| 1 GiB | 49.0% | 53.7% |
| 2 GiB | 66.3% | 78.2% |
| 4 GiB | 81.1% | 81.1% |

小容量下 fake store 略差，因为它在 **请求结束时整段保存**，而 offloading 边算边存。
两者在容量足够时收敛到同一上限。

### 14.4 传输计时（2026-10-28 补齐）

最初版本 worker 是 no-op，TTFT 不含 KV 读取时间（4G 时 7.9ms）。
补齐方式：

1. 新增 `SimulatedStoreWorker`（vLLM 模拟树）：在虚拟时钟上排 load/store，
   提供 `get_finished()` 与 `next_completion()`
2. 连接器改为**异步加载**（`get_num_new_matched_tokens` 返回 `(need, True)`），
   `start_load_kv` 按 `字节数 / load_gbps` 提交传输
3. 传输完成后 `get_finished` 返回 recving，调度器放行

实测（4 GiB store，线性时间模型）：

| 带宽 | fake AscendStore（计时） | CPU offloading |
| :-- | :-- | :-- |
| 10 GB/s | 21.0 ms | 21.7 ms |
| 25 GB/s | 13.4 ms | 13.7 ms |
| 50 GB/s | 10.9 ms | 11.1 ms |

**两条路径基本重合**，说明 fake connector 的时序建模与 offloading 代理一致。

### 14.5 使用建议

| 目的 | 用哪个 |
| :-- | :-- |
| 命中率 / 驱逐 / 容量阈值 | fake AscendStore（真实 kvpool 语义） |
| 带宽 → TTFT | 两者皆可，数字一致 |

## 15. P0/P1/P2：本机最大化验证 layerwise 复用

> 目标：只有本机（无 NPU、无 Mooncake）时，把"layerwise KV buffer 复用"验证到尽可能深。

### 15.3 P2：24 公共前缀的空跑（fake AscendStore）

工作负载：24 个公共前缀（每个 2048 tokens）× 24 会话 × 6 轮（每轮新增 512），HBM 1 GiB。

| 配置 | 命中率 | 被驱逐 | 未命中 tokens | mean TTFT | p90 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **1 个前缀**，store 8 GiB | 86.1% | 1/144 | 1,536 | 11.0 ms | 14.1 ms |
| **24 个前缀**，store 16 GiB | 80.0% | 0/144 | 0 | 18.6 ms | 28.9 ms |
| **24 个前缀**，store 8 GiB | 54.2% | 93/144 | 142,803 | 77.2 ms | 215.0 ms |
| **24 个前缀**，store 2 GiB | 46.7% | 120/144 | 184,276 | 83.3 ms | 228.2 ms |

两个结论：

1. **24 个前缀的容量需求是 1 个前缀的 24 倍**：本例工作集约 13.1 GiB，
   store 8 GiB 只覆盖一半 → 命中率 54%，p90 冲到 215 ms（反复驱逐/重载）
2. **容量给够后回到上限**：store 16 GiB 时 80.0%（上限 ≈ 1 − 512/3584 ≈ 85.7%），
   TTFT 18.6 ms，无驱逐

对应到线上：24 个 140K 前缀 ≈ 24 × 12.3 GiB ≈ **295 GiB** 的 store 容量，
否则命中率会随容量线性掉。
