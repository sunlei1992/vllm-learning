# 09 调度层可观测性与性能测量

> 面向「改调度、不改算子」的性能优化：怎么证明调度决策变了、变好了、没白改。

## 1. 核心问题

1. 调度层没有 kernel 可以 profile，观测点在哪？
2. 内置机制各自回答什么问题、开销多大、怎么开？
3. 调度器**自身**的 CPU 开销怎么量？（内置指标其实不直接给）
4. 怎么做可重复的 A/B，不被噪声和「平均值」骗？

## 2. 一句话总结

vLLM 的调度可观测性由三层组成：**请求级时间分解**（queue / prefill / decode）、**每步调度快照**（running / waiting / KV / batch 组成）、**系统级聚合**（Prometheus / 日志 / bench）。调度优化的第一指标是 `request_queue_time` 与每步 batch 组成，而不是 TTFT / TPOT 本身——后者是「调度 + 执行」的混合结果。

## 3. 三层观测模型

```
请求级   arrival ──QUEUED──> SCHEDULED ──first token──> last token
                    └ queue ┘   └──── prefill ────┘   └─ decode ─┘
                        ↑ 调度器直接决定              ↑ 调度 + batch 形状共同决定

每步级   Iteration(i): ctx_reqs / ctx_tokens / gen_reqs / gen_tokens / elapsed / KV%

系统级   throughput、TTFT/TPOT/E2EL 分布、goodput、preemptions、waiting_by_reason
```

| 层级 | 回答的问题 | 主要机制 | 开销 |
|---|---|---|---|
| 请求级 | 这个请求慢在排队还是慢在算？ | OTel span、per-request metrics、`request_*_time_seconds` 直方图 | 低（span 需显式开） |
| 每步级 | 这一步调度出了什么 batch？队列多长？ | `--enable-logging-iteration-details`、`SchedulerStats`、自定义 StatLogger | 中（每步一条日志） |
| 系统级 | 整体吞吐/延迟/公平性变好没有？ | 统计日志、Prometheus `/metrics`、`vllm bench` | 低 |

## 4. 内置机制清单

### 4.1 周期统计日志（默认开启）

默认每 **10 秒**一行（`VLLM_LOG_STATS_INTERVAL`，`vllm/envs.py:848`），由 `LoggingStatLogger.log()` 拼出（`vllm/v1/metrics/loggers.py:256`）：

```text
Engine 000: Avg prompt throughput: 123.4 tokens/s, Avg generation throughput: 567.8 tokens/s,
Running: 8 reqs, Waiting: 2 reqs, GPU KV cache usage: 45.6%, Prefix cache hit rate: 12.3%
```

有 deferred / preemption 时会追加 `Deferred: N reqs`、`Preemptions: N`。

| 字段 | 调度侧含义 |
|---|---|
| `Running` | 当前 batch 里的请求数，受 `max_num_seqs` 限制 |
| `Waiting` | 排队请求数（`num_waiting + num_skipped_waiting`） |
| `Deferred` | 被瞬态约束推迟的请求（LoRA 预算 / KV transfer / blocked） |
| `Preemptions` | 累计抢占次数；运行中请求「自己长大」撑爆 KV 时会出现 |
| `GPU KV cache usage` | KV 水位；长期贴近 100% 说明准入/抢占在起作用 |
| `Prefix cache hit rate` | 最近 1000 次请求的块命中率，APC 效果 |

调参：`VLLM_LOG_STATS_INTERVAL=1 vllm serve ...` 把采样频率提到 1s；`--disable-log-stats` 完全关闭（注意：per-request metrics 与 `--kv-cache-metrics` 依赖它）。

### 4.2 每步 iteration details（调度策略的第一现场）

开关：`--enable-logging-iteration-details`（`vllm/config/observability.py:73`）。每个 engine step 输出一行（`loggers.py:168`）：

```text
Engine 000: Iteration(12): 2 context requests, 512 context tokens,
7 generation requests, 7 generation tokens, iteration elapsed time: 12.34 ms,
GPU KV cache usage: 45.6%
```

这正是「chunked prefill 有没有生效、batch 有没有喂满、新请求什么时候被放进来」的直接证据。做调度实验时，它比 10s 聚合日志有用得多。

**两个必须知道的细节：**

1. `elapsed_ms` 的计时范围是 `vllm/v1/engine/core.py:598` 的 `with capture_iteration_details(...)`，包住的是 `future.result()` + `sample_tokens()`，即**模型执行到出 token 的墙钟时间**；它**不包含** `Scheduler.schedule()` 和 `update_from_output()`。所以它回答「这一步执行多慢」，不回答「调度本身多慢」。
2. 它是**每步一条 INFO**，压测时是 firehose。建议只在短时间窗口开，或改造成「每 N 步汇总一次」（见 §4.7 的子类写法）。

### 4.3 Prometheus `/metrics`（生产与压测的主力）

`PrometheusStatLogger`（`loggers.py:443`）把所有指标挂在 API server 的 `/metrics`，指标名带 `vllm:` 前缀；counter 暴露时会被加 `_total`。

**队列 / 调度状态**

| 指标 | 类型 | 读法 |
|---|---|---|
| `vllm:num_requests_running` | Gauge | batch 内请求数 |
| `vllm:num_requests_waiting` | Gauge | 排队总数（含 deferred） |
| `vllm:num_requests_waiting_by_reason{reason="capacity"\|"deferred"}` | Gauge | **capacity**=没有调度容量/KV；**deferred**=瞬态约束推迟（`loggers.py:513`） |
| `vllm:num_preemptions_total` | Counter | 抢占次数；KV 压力与策略的直接信号 |
| `vllm:kv_cache_usage_perc` | Gauge | KV 水位（0–1） |
| `vllm:iteration_tokens_total` | Histogram | **每步实际计算 token 数** = computed prompt + generation（`loggers.py:1205`），衡量 batch 喂得满不满 |

**请求级时间分解（调度贡献的核心）**

| 指标 | 含义 |
|---|---|
| `vllm:request_queue_time_seconds` | **QUEUED → 首次 SCHEDULED**，纯排队，调度器直接造成 |
| `vllm:request_prefill_time_seconds` | SCHEDULED → 首个 token |
| `vllm:request_decode_time_seconds` | 首 token → 末 token |
| `vllm:request_inference_time_seconds` | SCHEDULED → 末 token（prefill+decode） |
| `vllm:request_prefill_kv_computed_tokens` | 扣掉缓存命中后的真实 prefill 计算量 |
| `vllm:time_to_first_token_seconds` | TTFT = queue + prefill（含前端处理），**不要拿它单独归因调度** |
| `vllm:inter_token_latency_seconds` | ITL / TPOT |
| `vllm:e2e_request_latency_seconds` | 端到端 |
| `vllm:request_success_total{finished_reason="stop"\|"length"\|"abort"}` | 完成/截断/中止 |

**前缀缓存与 token 来源**

| 指标 | 含义 |
|---|---|
| `vllm:prefix_cache_queries_total` / `vllm:prefix_cache_hits_total` | 本地 APC 查询/命中 |
| `vllm:prompt_tokens_by_source{source="local_compute"\|"local_cache_hit"\|"external_kv_transfer"}` | **prompt token 花在哪**，直接量化 APC / KV connector 的收益 |
| `vllm:prompt_tokens_cached` | 被跳过的 prompt token |
| `vllm:external_prefix_cache_queries_total` / `_hits_total` | 外部（connector）前缀缓存 |

**按需开启的高级指标**

| 开关 | 指标 / 输出 | 用途 |
|---|---|---|
| `--kv-cache-metrics`（`--kv-cache-metrics-sample` 默认 0.01） | `vllm:kv_block_lifetime_seconds`、`_idle_before_evict_seconds`、`_reuse_gap_seconds` | KV 块驻留/复用，看缓存是被「占着」还是「真有用」 |
| `--enable-mfu-metrics` | `vllm:estimated_flops_per_gpu_total`、`_read_bytes_per_gpu_total`、`_write_bytes_per_gpu_total`；日志 `MFU: x TF/s/GPU y GB/s/GPU` | 估算算力/带宽利用，判断 batch 形状是否让硬件吃饱 |
| `--cudagraph-metrics` | 仅日志：padding/unpadded token 数与 dispatch 频率 | CUDA graph 按 batch size 分桶带来的 padding 浪费 |
| `--enable-layerwise-nvtx-tracing` | NVTX 逐层标记 | 偏算子/逐层，不是调度层首选 |

离线用法：`LLM.get_metrics()` 直接拿内存里的 Prometheus 快照（`vllm/v1/metrics/reader.py:70`），不用起 server。

> 多 API server（`--api-server-count > 1`）时统计日志会被禁用（`loggers.py` 有 warning），Prometheus 走多进程模式；DP 场景每个 engine 有独立 `engine` label，可用 `--aggregate-engine-logging` 聚合成一行。

### 4.4 每请求 metrics（直接回传给客户端）

开关：`--enable-per-request-metrics`。它复用 stats logging 已经采集的 `RequestStateStats` 时间戳，在响应里多挂一个 `metrics` 对象（`build_per_request_timing_metrics`，`vllm/entrypoints/generate/base/serving.py:48`；文档 `docs/features/per_request_metrics.md`）。

```bash
vllm serve Qwen/Qwen3-0.6B --enable-per-request-metrics
# 注意：不能同时给 --disable-log-stats，启动时会直接报错
```

非流式响应（`/v1/chat/completions` 与 `/v1/completions` 都支持）：

```json
"metrics": {
  "time_to_first_token_ms": 85.2,
  "generation_time_ms": 1240.5,
  "queue_time_ms": 12.3,
  "mean_itl_ms": 9.1,
  "tokens_per_second": 103.2
}
```

字段全部来自 engine core 的四个单调时间戳（`RequestStateStats`）：

```text
前端 arrival
   │  tokenize / 多模态预处理（不计入 metrics）
   ▼
QUEUED ───────── queue_time_ms ─────────> SCHEDULED
(queued_ts)                                (scheduled_ts)
                                               │
                                               │ time_to_first_token_ms
                                               │ （prefill，含 chunk 间隙/抢占）
                                               ▼
                                         first token (first_token_ts)
                                               │
                                               │ generation_time_ms
                                               │ （decode，含抢占/重算）
                                               ▼
                                         last token (last_token_ts)

tokens_per_second 的区间 = SCHEDULED → last token（= ttft + generation）
```

| 字段 | 区间 | 公式 | 包含 | 不包含 | 何时为 `null` |
|---|---|---|---|---|---|
| `queue_time_ms` | QUEUED → 首次 SCHEDULED | `scheduled_ts - queued_ts` | engine core 队列里的排队；等 KV、等并发槽位、等优先级 | 前端 tokenize/网络；**被抢占后再次排队的时间** | 时间戳缺失（如排队中被 abort） |
| `time_to_first_token_ms` | SCHEDULED → 首 token | `first_token_ts - scheduled_ts` | prefill 计算、chunked prefill 的多个 step 间隙、prefill 期间的抢占、首 token 采样 | **排队时间**、前端处理 | 首 token 未产生就结束 |
| `generation_time_ms` | 首 token → 末 token | `last_token_ts - first_token_ts` | 所有 decode step；decode 期间的抢占/重算 | 排队、prefill、首 token 之前的一切 | 首/末 token 时间戳缺失 |
| `mean_itl_ms` | 首 token → 末 token，按间隔平均 | `generation_time_ms / (N - 1)`，N=输出 token 数 | 平均每个 output token 的间隔，含抢占造成的停顿 | prefill、排队 | `N <= 1`（只生成 1 个 token） |
| `tokens_per_second` | SCHEDULED → 末 token | `N / (last_token_ts - scheduled_ts)` | 输出 token 数 ÷（prefill + decode） | 排队、前端处理 | 区间 <= 0 或时间戳缺失 |

三个等式：

```text
queue + time_to_first_token + generation = last_token_ts - queued_ts
                                        ≈ engine core 内的端到端
用户感知 E2E ≈ 前端处理 + queue + time_to_first_token + generation + 网络

tokens_per_second = N / (time_to_first_token + generation)
mean_itl_ms      = generation / (N - 1)
```

用上面的示例反推：`queue 12.3 + ttft 85.2 = 97.5 ms` 到首 token；`N ≈ 1240.5 / 9.1 + 1 ≈ 137` 个 token；`tps ≈ 137 / (85.2 + 1240.5) × 1000 ≈ 103.3`，与 103.2 吻合。所以这组数字对应「排队 12ms、prefill 85ms、decode 1.24s、输出约 137 token」的一次请求。

**怎么用它定位调度问题：**

| 现象 | 大概率原因 |
|---|---|
| `queue_time` 高，`ttft`/`generation` 正常 | 准入/排队问题：KV 不够、`max_num_seqs` 太小、优先级被压 |
| `queue_time` 低，`ttft` 高 | prefill 慢：prompt 太长、prefix cache 没命中、chunked prefill 预算太小、prefill 期间被抢占 |
| `queue_time` 低，`ttft` 低，`mean_itl` 高 | decode 阶段慢：batch 太大、KV 带宽/抢占、decode 期间被重新 prefill |
| `mean_itl` 高但 `queue_time` 低 | 不一定是调度排队，可能是 **KV 压力导致抢占/重算**（这段时间算在 generation 里，不算 queue） |
| `tokens_per_second` 低但 `mean_itl` 也低 | 输出太短，prefill 在分母里占比高；看 `ttft` 而不是 `itl` |

**最容易误读的四点：**

1. **`time_to_first_token_ms` 不是用户感知的 TTFT**。它从「被调度」开始算，**不含排队**；用户感知 TTFT ≈ `queue_time_ms + time_to_first_token_ms` + 前端处理。
2. **被抢占的时间不算进 `queue_time_ms`**。`scheduled_ts` 只记第一次被调度（源码里明确 `# ignore preemptions`），所以抢占后重新排队的时间会算进 `prefill`（首 token 前）或 `generation`（首 token 后）。
3. **`mean_itl_ms` 含抢占停顿**。它不是纯 kernel 的 ITL；如果请求在 decode 中被抢占、KV 被换出再重算，这段也会摊进平均。
4. **`tokens_per_second` 含 prefill**。它通常小于 `1000 / mean_itl_ms`（除非 prefill 比一个 ITL 还短）；输出越短、prompt 越长，差距越大，不要拿它当纯 decode 速率。

另外，`metrics` 里的所有时间都是 **engine core 进程内的单调时钟**，不含 HTTP 排队、网络、客户端反序列化；跨进程/跨机器比较绝对值没有意义，只适合同一实例内做分布和归因。

客户端读法（`metrics` 不是 OpenAI 标准字段，SDK 会放进 `model_extra`）：

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="dummy")
resp = client.chat.completions.create(
    model="Qwen/Qwen3-0.6B",
    messages=[{"role": "user", "content": "hello"}],
    max_tokens=64,
)
print(resp.model_extra.get("metrics"))
```

流式请求必须显式要 usage，否则最后的 usage chunk 不会发，metrics 也就没有落点：

```python
stream = client.chat.completions.create(
    model="Qwen/Qwen3-0.6B",
    messages=[{"role": "user", "content": "hello"}],
    max_tokens=64,
    stream=True,
    stream_options={"include_usage": True},  # 或服务端 --enable-force-include-usage
)
for chunk in stream:
    if chunk.usage is not None:              # 最后一个 usage chunk
        print(chunk.model_extra.get("metrics"))
```

限制：

- `n > 1` 时抑制（时间戳只属于其中一条流，无法归因），返回 `"metrics": null`；`/v1/completions` 的多 prompt 请求同理。
- 只覆盖 `/v1/chat/completions` 和 `/v1/completions`；`/v1/responses` 目前没有接这个字段（源码里只有 chat/completion 调 `build_per_request_timing_metrics`）。
- 它是**客户端侧**的逐请求数据，`vllm bench serve` 不会读它（bench 用自己的客户端计时）。要批量统计 queue time 分布，得自己写客户端收集，或直接看 Prometheus 的 `vllm:request_queue_time_seconds` 直方图。
- 高并发下计算 + 序列化有 CPU 开销，官方文档建议先按自己的 workload 压一遍再决定是否常开。
- 离线实验没有 HTTP 层，但 `RequestOutput.metrics`（`vllm/outputs.py:135`）带的是原始 `RequestStateStats`，可以自己用 `scheduled_ts - queued_ts` 算 queue time，不必起 server。

批量收集 queue 分布的最小脚本（异步发请求，取响应里的 `metrics`）：

```python
import asyncio, aiohttp

URL = "http://localhost:8000/v1/chat/completions"
PAYLOAD = {"model": "Qwen/Qwen3-0.6B",
           "messages": [{"role": "user", "content": "hello"}],
           "max_tokens": 64}

async def one(session):
    async with session.post(URL, json=PAYLOAD) as r:
        return (await r.json()).get("metrics")

async def main():
    async with aiohttp.ClientSession() as s:
        rows = await asyncio.gather(*(one(s) for _ in range(200)))
    q = sorted(r["queue_time_ms"] for r in rows
               if r and r.get("queue_time_ms") is not None)
    print("n =", len(q), "p50 =", q[len(q) // 2], "p99 =", q[int(len(q) * 0.99)], "max =", q[-1])

asyncio.run(main())
```

### 4.5 OpenTelemetry tracing（看单请求的排队 vs 计算）

开关：`--otlp-traces-endpoint <url>` + `--collect-detailed-traces=model|worker|all`（`vllm/config/observability.py:36`）。

每个请求一个 `llm_request` span（`vllm/v1/engine/output_processor.py:753`），attributes 直接给出分解：

```text
gen_ai.latency.time_in_queue
gen_ai.latency.time_to_first_token
gen_ai.latency.time_in_model_prefill
gen_ai.latency.time_in_model_decode
gen_ai.latency.time_in_model_inference
gen_ai.latency.e2e
```

在 Jaeger/Tempo 里能一眼看出「这个请求 80% 时间在排队」。`--collect-detailed-traces` 会加 model/worker 级 span，有额外开销，只在定位问题时开。

### 4.6 自定义 StatLogger（每步回调，不改调度器）

`StatLoggerBase`（`loggers.py:44`）每步都会收到 `SchedulerStats` + `IterationStats`。注册方式：

- 进程内：`LLMEngine(..., stat_loggers=[MyLogger])`（`vllm/v1/engine/llm_engine.py:58`）
- 服务化：entry point group `vllm.stat_logger_plugins`，类需继承 `StatLoggerBase`，构造签名 `(vllm_config, engine_index)`（`vllm/plugins/__init__.py:26`、`docs/design/plugin_system.md`）

能拿到：running/waiting/KV、prefix cache 统计、每步 prefill/generation token、TTFT/ITL 列表、完成请求的 queue/prefill/decode 时间、preemption 计数。

拿不到：`schedule()` 内部的分支耗时、每个候选请求为什么被跳过——这些要进调度器内部（§4.7）。

### 4.7 给 `Scheduler.schedule()` 本身埋点

内置没有任何「调度器 CPU 时间」指标。最小侵入的做法是用 `--scheduler-cls` 子类化（`vllm/config/scheduler.py:117`，`--scheduler-cls` 已在本机 `vllm serve --help=all` 中确认存在）：

```python
# my_scheduler.py（放在 PYTHONPATH 上）
import time

from vllm.logger import init_logger
from vllm.v1.core.sched.scheduler import Scheduler

logger = init_logger(__name__)


class TimedScheduler(Scheduler):
    def schedule(self, throttle_prefills: bool = False):
        t0 = time.perf_counter()
        out = super().schedule(throttle_prefills)
        dt_ms = (time.perf_counter() - t0) * 1e3

        self._acc_ms = getattr(self, "_acc_ms", 0.0) + dt_ms
        self._acc_steps = getattr(self, "_acc_steps", 0) + 1
        if self._acc_steps >= 100:
            logger.info(
                "sched: avg %.3f ms/step over %d steps, last tokens=%d, "
                "running=%d waiting=%d",
                self._acc_ms / self._acc_steps,
                self._acc_steps,
                out.total_num_scheduled_tokens,
                len(self.running),
                len(self.waiting),
            )
            self._acc_ms = 0.0
            self._acc_steps = 0
        return out
```

```bash
PYTHONPATH=/path/to/dir vllm serve <model> --scheduler-cls my_scheduler.TimedScheduler
```

注意：

- EngineCore 默认在独立进程，日志会经 vLLM 的日志转发出来；本地调试可配 `VLLM_ENABLE_V1_MULTIPROCESSING=0` 让 Scheduler 跑在主进程，方便断点。
- 也可以 monkey-patch `Scheduler.schedule`（本仓库 `tmp/sim_steps.py` 就是这么做逐步记录的），但只建议在实验脚本里用。
- `VLLM_TRACE_FUNCTION=1` 是 Python 级全函数 trace，开销极大，只用于 debug 挂起/崩溃，不是性能测量工具。
- 调度开销通常被 GPU 执行掩盖：只有当 `schedule()` 慢到超过 GPU step 时间，或 GPU 已经饱和、CPU 成为瓶颈时，才会体现在吞吐上。所以要**同时**看 `sched ms/step` 与 `iteration_details.elapsed_ms` 的比例。

## 5. `vllm bench` 工具链

`vllm bench` 子命令（本机实测）：`latency`、`mm-processor`、`serve`、`startup`、`sweep`、`throughput`。

| `vllm bench sweep serve` | **扫 `vllm serve` 参数**（`max_num_seqs`、`max_num_batched_tokens`、chunked prefill、scheduler-cls 等），每组跑 N 次 | `--serve-params`、`--bench-params`、`--num-runs`、`--dry-run`、`--resume` |

## 6. 调度 A/B 方法论

### 6.1 先分清三类改动

| 改动类型 | 例子 | 主要看什么 |
|---|---|---|
| 策略（谁先跑） | FCFS / priority / 短请求优先 / LPM | `queue_time` 分布、分请求类别的 TTFT、goodput、公平性 |
| 批处理（batch 多大） | `max_num_seqs`、`max_num_batched_tokens`、chunked prefill 阈值 | `iteration_tokens_total`、KV 水位、preemption、吞吐 |
| 调度开销（CPU） | 复杂打分、频繁排序、每步分配 | 自定义 `sched ms/step`、`iteration_details.elapsed_ms`、吞吐拐点 |

### 6.2 固定变量

- workload：dataset、input/output 长度分布、到达过程（`--request-rate` + `--burstiness`）、`--num-prompts` 足够大。
- 引擎：模型、TP/PP/DP、`gpu_memory_utilization`、KV 容量、`block_size`、prefix caching 开关。
- 测量：预热（JIT/compile/cudagraph capture 完成后再计时）、`--num-runs ≥ 3`、报告分位数而非均值。

### 6.3 关键教训：策略常常只是「重新分配延迟」

本仓库 `sim_policy.py` 的空跑实验（FCFS / 短优先 / 长优先，同一 workload）：

| 策略 | makespan | mean TTFT | max TTFT | mean TPOT |
|---|---|---|---|---|
| FCFS | 205.45 | 90.94 | 171.10 | 14.98 |
| 短优先 | 205.45 | **56.50** | 181.10 | 20.39 |
| 长优先 | 205.45 | 143.04 | **152.10** | **8.57** |

三者**总吞吐完全相同**，变的是延迟在请求类别之间的分配。所以：

- 短优先把 mean TTFT 降了 38%，但 max TTFT 和 mean TPOT 都变差；长优先正好相反。只看一个均值会漏掉这种重分配。
- 必须按请求类别 + 分位数（p50/p99）+ goodput 看，必要时看公平性指标（如按类别等待时间的方差）。

### 6.4 区分「调度决策变了」和「执行时间变了」

在真机上，调度改动常常同时改变 batch 形状 → 改变 kernel 效率。若只想验证调度行为本身，用本仓库的 simulate-forward 时间模型（`zero` / `linear` / `table`）把算力固定，先看调度指标（queue time、step 数、batch 组成）是否按预期变化，再上真机确认端到端收益。

## 7. 最小配方

```bash
# 1) 开观测：每步明细 + KV 驻留 + MFU；日志 1s 一次
VLLM_LOG_STATS_INTERVAL=1 \
vllm serve Qwen/Qwen3-0.6B \
  --enable-logging-iteration-details \
  --kv-cache-metrics \
  --enable-mfu-metrics

# 2) 另开终端抓 Prometheus（压测期间周期性采样）
while true; do
  curl -s localhost:8000/metrics | grep -E 'vllm:(num_requests|kv_cache_usage|request_queue_time|iteration_tokens|num_preemptions|prompt_tokens_by_source)' \
    >> metrics.log
  sleep 1
done

# 3) 压测并保存 JSON
vllm bench serve \
  --dataset-name random --random-input-len 1024 --random-output-len 128 \
  --num-prompts 200 --request-rate 8 \
  --percentile-metrics ttft,tpot,itl,e2el --metric-percentiles 50,90,99 \
  --goodput ttft:500 --save-result --result-dir results

# 4) 扫调度参数（自动起停 server、每组 3 次）
vllm bench sweep serve --serve-cmd 'vllm serve Qwen/Qwen3-0.6B' \
  --bench-cmd 'vllm bench serve --dataset-name random --random-input-len 1024 --random-output-len 128 --num-prompts 200' \
  --serve-params serve_hparams.json --num-runs 3 --output-dir results

# 5) 出图：x 轴取一个扫过的参数，curve 取另一个
vllm bench sweep plot results/<exp> --var-x max_num_seqs --var-y median_ttft_ms \
  --curve-by max_num_batched_tokens
```

## 8. 坑与注意事项

1. **`elapsed_ms` 不是调度耗时**：它包住 `future.result()` + sampling，不含 `schedule()`。别拿它当调度器 CPU 指标。
2. **日志本身有开销**：`--enable-logging-iteration-details` 每步一条 INFO；压测对比时两组要么都开、要么都关。
3. **KV 容量决定结论**：KV 给太小会把策略差异淹没在「准入排队」里，看起来像「加并发没用」。容量要按真实硬件对齐。
4. **prefix cache 会改变 prefill 量**：对比调度策略时要么都开、要么都关；用 `prompt_tokens_by_source` 确认命中差异。
5. **DP 下指标是分 engine 的**：Prometheus 有 `engine` label；日志用 `--aggregate-engine-logging` 聚合，否则每行只代表一个 engine。
6. **多 API server 会关统计日志**：`--api-server-count > 1` 时 `LoggingStatLogger` 被禁用，别以为是 bug。
7. **`n > 1` / 多 prompt 请求没有 per-request metrics**：归因不了单条流。
8. **goodput 阈值要按业务定**：TTFT 500ms 和 2s 会选出完全不同的最优配置。
9. **异步调度（`--async-scheduling`）会改变重叠关系**：时间戳仍有效，但 queue/prefill 的边界语义与同步模式不完全一样，A/B 时不要混用两种模式。
