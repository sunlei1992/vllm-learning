# 13 性能调试方法论：从 TTFT/TPOT/吞吐到瓶颈归因

## 0. 元信息

- 日期：2026-11-05
- 来源：① vLLM 官方文档 `docs/contributing/profiling.md`、`docs/benchmarking/*`、`docs/configuration/optimization.md`（本地 `vllm-src`，0.28.0）；
  ② 源码核对（`vllm/v1/metrics/loggers.py`、`vllm/config/profiler.py`、`vllm/v1/worker/gpu_worker.py`、`.buildkite/performance-benchmarks/tests/*.json`）；
  ③ 网络资料：vLLM profiling/benchmarking 文档、GuideLLM、NVIDIA AIPerf 博客、vllm-ascend 的 `service_profiling_guide.md`。
- 前置阅读：`09-调度层可观测性与性能测量.md`（讲"调度层能看到什么"），本篇讲"**怎么归因、用哪把尺子**"。

## 1. 一句话结论

vLLM 开发者不是「跑一次 profiler 看哪个 kernel 慢」，而是**分层归因**：先用压测把端到端指标钉在可复现的 workload 上（L1），再用请求级时间分解判断慢在排队还是慢在算（L2），再用每步 trace 注解判断这一步的 batch 形状与 GPU 空泡（L3），最后才下到 kernel / roofline（L4），并用 CI 看板防回归（L5）。**TTFT/TPOT 本身不是归因单位，`queue_time` / batch 组成 / 每步 wall-clock 才是。**

## 2. 为什么必须先分层

一个请求的时间轴（源码里的状态机，`vllm/v1/metrics/stats.py:218` `RequestStateStats`）：

```
arrival(前端墙钟) ──QUEUED──> SCHEDULED ──first_token──> last_token
                    └queue ┘   └── prefill ──┘   └── decode ──┘
                    调度器决定    调度 + batch 形状      batch 形状 + KV 带宽/通信
```

对应三个直方图（`loggers.py:922/942/952`）：`vllm:request_queue_time_seconds`、
`vllm:request_prefill_time_seconds`、`vllm:request_decode_time_seconds`。于是：

- **TTFT ≈ queue_time + prefill_time**（+ 前端/分词/首包开销）
- **TPOT ≈ decode 每步 wall-clock / 每步被采纳 token 数**

所以 TTFT 高只有两种可能：没人给你算（排队），或者算得慢（prefill 太长/没 chunk）。TPOT 高也只有两种：**每步变慢**（compute/带宽/通信）或**每步装得太多**（batch 太大导致 kernel 时间线性上升）或**每步在重算**（抢占重算、prefix 未命中、KV 压力导致 admission 反复重试）。

## 3. L0：先把尺子做稳（否则后面全是噪声）

| 事项 | 做法 | 为什么 |
| :-- | :-- | :-- |
| 客户端不能成为瓶颈 | 用 `vllm bench serve`（C++/asyncio 并发）或 GuideLLM / AIPerf（多进程） | 单进程 Python 压测器在几十并发就 GIL 打满，测到的是客户端 |
| 必须 `stream=True` | vLLM bench 默认带 stream；AIPerf 要显式 `--streaming` | 不流式就没法定义 TTFT/ITL，服务端会攒完再发 |
| 固定输出长度 | `--ignore-eos`、`--random-output-len`（或 AIPerf `min_tokens`+`ignore_eos`） | 否则模型提前 EOS，吞吐数字不可复现 |
| 冷启动要丢掉 | 至少整轮 warmup，`--num-warmups` 不够 | 首次会触发 CUDA graph capture / Triton JIT / 权重搬运（本仓库实验 E 实测冷启动 TTFT 差 2 倍） |
| 多轮取中位数 | `vllm bench sweep serve --num-runs 3` | 官方默认每组 3 次 |
| 每组之间清状态 | sweep 会自动调 `/reset_*_cache` | 否则 prefix cache 跨组泄漏 |
| workload 形状要成矩阵 | 官方 CI：`(128/128, 128/2048, 2048/128, 2048/2048) × max_concurrency {12,16,24,32,64,128,200} × qps {4,8,16,32,inf}`（`.buildkite/performance-benchmarks/tests/serving-tests.json`） | 长输入/长输出/两端都长，瓶颈完全不同 |

## 4. L1：端到端指标的口径（最容易被误读的地方）

`docs/benchmarking/cli.md` 明确写了三者定义，且**术语跨工具不统一**：

- **TTFT**：发请求 → 收到第一个流式包。
- **ITL**：相邻两个流式包之间的间隔，**按包采样**。
- **TPOT**：`(E2E − TTFT) / (output_tokens − 1)`，**按请求采样**。

**投机解码下 ITL ≠ TPOT**：一个包可能塞了 K 个被采纳 token，ITL 只记包间隔（不补 0 间隔），TPOT 把解码时间摊到每个 token。所以用 ITL 评估投机解码会高估。

要看的是**分布**而不是均值，官方推荐 `--metric-percentiles`；长尾（p99）才是业务 SLA 的真正约束。

**goodput 是调度优化的第一指标**（`benchmarks/serve.py:562` `request_goodput`，CLI `--goodput ttft:...,tpot:...,e2el:...`）：只统计满足 SLO 的请求吞吐。原因见本仓库实验与 `10-调度优化测试工作流.md`：**很多策略只是"重新分配延迟"，总吞吐和 makespan 完全不变**（FCFS/短优先/长优先 makespan 都是 205.45）。用平均值看，会得出"策略有效"的假结论。

## 5. L2：请求级分解——"慢在排队还是慢在算"

```bash
# 每步明细（1s 采样），压测时短窗口开
VLLM_LOG_STATS_INTERVAL=1 vllm serve <model> --enable-logging-iteration-details
```

默认 10s 的统计行（`loggers.py:256`）：

```text
Avg prompt throughput: 123.4 tokens/s, Avg generation throughput: 567.8 tokens/s,
Running: 8 reqs, Waiting: 2 reqs, Preemptions: 0, GPU KV cache usage: 45.6%, Prefix cache hit rate: 12.3%
```

读法（配合 Prometheus 的 `vllm:request_queue_time_seconds` / `vllm:num_requests_waiting_by_reason`）：

| 观测 | 归因 | 下一步 |
| :-- | :-- | :-- |
| `Waiting` 持续 > 0，`Running` 卡在 `max_num_seqs` | 并发上限，纯排队 | 抬 `max_num_seqs`，或加 DP 副本；TTFT 由准入控制决定，别去查 kernel |
| `Waiting` 高但 `Running` 远小于 `max_num_seqs` | KV 不够 / 预算被 chunk 吃掉 | 查 `GPU KV cache usage`、`max_num_batched_tokens` |
| KV usage 长期 ~100% + `Preemptions` 增长 | 运行中请求"自己长大"撑爆 KV → 抢占重算 | TPOT 会跳变；这是系统级（容量）问题，不是算子问题 |
| `Prefix cache hit rate` 低但业务有共享前缀 | APC 没生效 / 前缀被驱逐 | 查 block 对齐、`--enable-prefix-caching`、调度分组（见实验 F） |
| 吞吐上不去、KV 也不满、Running 也上不去 | 算力或 HBM 带宽打满 | 进 L3/L4 |
| `elapsed` 每步抖动大、GPU util 不满 | **CPU 侧瓶颈**（scheduler / detokenize / Python 开销） | 进 L3 看空泡，`--async-scheduling`、IPC、开 graph |

## 6. L3：引擎单步——trace 注解是 vLLM 的独门武器

官方 profiler 唯一的"系统级"信息是**每步注解**（`vllm/v1/worker/gpu_worker.py:944` `annotate_profile`）。开 `--profiler-config.detailed_trace_annotation` 后，trace 里每个 iteration 的名字长这样：

```
execute_<总调度token>_context_<请求数>(sq<ctx新token和> sk<ctx总KV长度和> sqsq<Σq²> sqsk<Σq·k>)
                    _generation_<请求数>(sq<...> sk<...> sqsq<...> sqsk<...>)
```

- `sqsq = Σ query_len²`、`sqsk = Σ query_len · seq_len` 是 **QK^T 的算力代理量**，`sk = Σ seq_len` 是 **KV 读写量代理**。
- 用法：把 nsys 里每步的耗时和这串数字对齐 → 立刻能回答"这步慢是因为 token 多，还是因为 KV 长，还是因为 batch 里 ctx/gen 混杂"。**同一个 kernel 时间，在不同 batch 形状下含义完全不同**，这是纯 kernel profiling 给不了的。

同一层的其他开关：

| 手段 | 说明 |
| :-- | :-- |
| `--enable-layerwise-nvtx-tracing` | 逐层 NVTX range（带 input/output shape），**与 CUDA graph 不兼容**（`config/observability.py:60`），用于定位 TP/PP 通信 vs 计算的相对占比 |
| `VLLM_NVTX_SCOPES_FOR_PROFILING=1` | 给 scheduler 等关键路径加 NVTX scope |
| `--enable-mfu-metrics` | MFU（Model FLOPs Utilization）指标，直接把"算力用了百分之几"报出来 |
| `--enable-cuda-graph-metrics` | padded/unpadded token 数、graph dispatch 模式分布；**padding 浪费**是 TBT 的常见隐性来源 |
| `VLLM_ENABLE_V1_MULTIPROCESSING=0` | 调度器进主进程，可 monkey-patch hook 每步（本仓库 `tmp/sim_steps.py` 用法） |
| `VLLM_GC_DEBUG=1` / `{"top_objects":5}` | Python GC 在热路径上的开销（`docs/contributing/profiling.md` 末尾） |

> 注意：`VLLM_TRACE_FUNCTION=1` 是**调试卡死/崩溃**用的全函数调用记录（`vllm/logger.py:294`），不是性能工具，开了会慢到没法测。

## 7. L4：算子与 roofline——只在 L2/L3 指过来之后才做

### 7.1 三把 profiler（官方对比，`docs/contributing/profiling.md`）

| 工具 | 开销 | 场景 | 入口 |
| :-- | :-- | :-- | :-- |
| **Nsight Systems** | 低（首选做性能） | kernel 时间线、GPU 空泡、CUDA API、graph 内部、通信 | `nsys profile --trace-fork-before-exec=true --cuda-graph-trace=node ...`；服务器配合 `capture-range=cudaProfilerApi` + `--profiler-config.profiler cuda` |
| **PyTorch Profiler** | 中（有 stack/memory/shape/flops） | 需要栈、shape、显存归属 | `--profiler-config '{"profiler":"torch","torch_profiler_dir":"/abs/path"}'`，或 bench `--profile`，或 `/start_profile` `/stop_profile` |
| **Triton Proton** | 低（CUPTI） | Triton kernel 归因，hatchet 树/Chrome trace | `--enforce-eager --profiler-config '{"profiler":"proton",...}'`，`proton-viewer` 看树 |

官方口径的硬规矩：
- **只发几个请求**，trace 会非常大；`/stop_profile` flush 很慢（H100 + llama70b 100 请求约 10 分钟），不是卡死。
- `VLLM_WORKER_MULTIPROC_METHOD=spawn` 配合 nsys。
- 单卡/单 rank 先看，`nsys stats` 的 `cuda_gpu_kern_sum` 已能给出 GEMM / attention / norm / rope 的占比（官方示例里 GEMM 46%+15%+12%，FlashAttention 4.1%）。
- 有 CUDA graph 时 kernel 名会被折叠 → Proton 和 layerwise NVTX 都必须 `--enforce-eager`。

### 7.2 判断"算力 bound"还是"带宽 bound"

不要猜，用代理量算：`sqsq`（算力）与 `sk`（KV 读写）的比值就是这一步的**算术强度**；decode 阶段 seq_len 大、query_len=1，算术强度 ≈ 1，必然 HBM 带宽 bound；prefill 阶段 query_len 大，算术强度随 q 线性涨，走 compute bound。这解释了：

- decode TPOT 对 **batch 内总 KV 长度**（不是请求数）敏感 → KV 越长越慢；
- prefill 时间对 **token 数**近似二次/线性混合 → chunk 大小直接换 TTFT；
- 量化/FP8 收益主要在 decode（带宽省一半），prefill 收益小（compute bound）。

配套：`nvidia-smi dmon -s um`（SM util / mem util）、DCGM（AIPerf 可直接把 GPU 功耗/利用率/显存并到同一份结果里）。

### 7.3 算子级专用 bench（vLLM 自己的做法）

`benchmarks/kernels/`、`benchmarks/attention_benchmarks/`、`benchmarks/fused_kernels/`、`benchmarks/cutlass_benchmarks/`：**不跑端到端**，直接用固定 shape 扫 attention backend / GEMM tile / MoE kernel。改 kernel 时的标准做法是「先在 kernel bench 证明快，再用 `vllm bench serve` 证明端到端没退化」。

## 8. L5：防回归（vLLM 开发者日常真正在跑的东西）

- 每个 commit 带 `perf-benchmarks` label 触发 CI，结果发到公共看板 <https://hud.pytorch.org/benchmark/llms?repoName=vllm-project%2Fvllm>；同一页面还有 **Profiling traces** 表（PyTorch 基础设施的周更 continuous profiling）。
- 本地复现 CI：`bash .buildkite/performance-benchmarks/scripts/run-performance-benchmarks.sh`（`docs/benchmarking/dashboard.md`）。
- **SLA 自适应并发搜索**：CI 里除了静态扫并发，还有 `ENABLE_ADAPTIVE_CONCURRENCY=1` + `SLA_TTFT_MS=3000` / `SLA_TPOT_MS=100` 的二分探测，直接输出"满足 SLA 的最大并发"。这比"扫一条曲线自己看拐点"更适合做容量决策。
- 对比：`compare-json-results.py` / `vllm bench sweep plot` / `plot_pareto`（每用户 tok/s vs 每 GPU tok/s 的 Pareto 前沿）。

## 9. 症状 → 仪器 判定树（实操版）

```
TTFT 高
├─ queue_time 占比高 ──────────→ L2：Waiting/Running/KV 水位；抬并发或加副本；不要看 kernel
│   └─ 有 Preemptions/重试 ────→ KV 容量问题（准入/驱逐），查 block 预算
└─ prefill_time 占比高
    ├─ chunk 太小（TTFT 随预算下降）→ 抬 max_num_batched_tokens（代价：ITL 变差）
    ├─ 前缀没命中（prefill token 数 ≈ 全长）→ APC / prefix 亲和
    └─ 单请求 prefill 就慢 ─────→ L4：GEMM/attention kernel、TP 通信、PD 分离放置

TPOT/ITL 高（长尾）
├─ 每步 batch 太大（吞吐换延迟）──→ 降 max_num_seqs / 预算；看 iteration details
├─ KV 长 + 带宽 bound ──────────→ L4 roofline：量化 KV、GQA/MLA、降并发
├─ 抢占重算（KV 满）────────────→ 容量/准入；TPOT 会台阶式跳变
├─ 投机解码 K 波动 ────────────→ 看 ITL 与 TPOT 的差（包内多 token）
└─ 每步有空泡（GPU util 掉）───→ CPU bound：nsys 看 CPU 侧、开 async scheduling、减 Python 热路径

吞吐上不去
├─ SM util 高 / MFU 高 ────────→ 真算力 bound：量化、TP/EP、更大 batch
├─ SM util 低 / mem util 高 ───→ 带宽 bound：KV 压缩、量化权重
├─ 两者都低 ───────────────────→ 调度/CPU/通信串行：看空泡与 PP bubble
└─ 都正常但吞吐不线性 ─────────→ 客户端瓶颈、队列、tokenize、网络/SSE
```

## 10. Ascend（vllm-ascend）对照表

工具链与 GPU 侧**不同名但同构**，见 `vllm-ascend-src/docs/source/developer_guide/performance_and_debug/`：

| 目的 | GPU（vLLM） | NPU（vllm-ascend） |
| :-- | :-- | :-- |
| 算子级 | nsys / torch profiler / proton | **Ascend PyTorch Profiler**（同一套 `--profiler-config '{"profiler":"torch",...}'`，产出 `*_ascend_pt` 目录）；`msprof` |
| 算子结果文件 | `cuda_gpu_kern_sum` | `kernel_details.csv` / `op_statistic.csv` / `step_trace_time.csv`（调度） |
| 可视化 | Perfetto / nsys GUI | **MindStudio Insight**（吃 `trace_view.json`） |
| 服务框架级（= 我们的 L2） | Prometheus + iteration details | **MS Service Profiler**：`request.csv`（每请求）、`kvcache.csv`、`batch.csv`（每 batch 调度） |
| 关心域 | — | `Request;KVCache;ModelExecute;BatchSchedule;Communication`（`domain` 可裁剪采集量） |
| P/D 分离 | 分别 `/start_profile` | 同样**分别**对 P、D 打 `/start_profile`；主代理不转发，EPD 代理才广播 |

两个 Ascend 特有的坑：

1. **`VLLM_TORCH_PROFILER_DIR` 已废弃**（2026-01 起），必须用 `--profiler-config`；否则 `/start_profile` 直接 404。
2. Ascend profiler **默认开 Python stack**，数据量巨大且显著拖慢；采服务性能时必须 `torch_profiler_with_stack: false`。
3. `acl_prof_task_time_level`：`L0` 只有 dispatch+执行耗时（低开销）；`L1` 才带 ACL 接口与 H2D/D2H 拷贝延迟，看"是不是卡在数据搬运"必须 L1。

## 11. 坑与反模式

1. **拿 bench serve 的 TTFT 直接对比不同工具**：口径不同（是否含 tokenize / 是否含排队 / 是否按包）。看定义，不看名字。
2. **均值当结论**：调度策略几乎总在用长尾换均值；用 p99 + goodput。
3. **开着 profiler 报性能数字**：torch profiler 中开销，Python stack 更甚；官方明说 profiling 只给开发者用。
4. **CUDA graph 下做 kernel 归因**：图内 kernel 折叠、NVTX 失效，必须 eager。
5. **改了 kernel 就只跑 kernel bench**：端到端可能被调度/bandwidth 吃掉，必须再跑一次 serving。
6. **capacity 不匹配却做 P/D 或 chunk 结论**：KV 给太小会被准入卡成排队，看起来像"加 P 没用"（本仓库实验 D 的假象）。
7. **冷启动污染**：第一次跑包含 graph capture / JIT / 权重首访，整轮丢弃。
