## 2. 最重要的决策：查重（AGENTS.md 铁律）

**发现自己修好了 bug，第一反应想提 PR——但先查重救了你**：

- vLLM 的 AGENTS.md 明确规定：*"If an open PR already addresses the same fix, do not open another."*
- 用 GitHub API 搜索（`api.github.com` 可用，`github.com` 被墙）发现 **PR #51471** 已存在且活跃（作者就是原始 CPU MLA 后端 #49453 的作者，今天还在更新）
- **结论：我们自研的 SDPA 修复方向与社区一致，但架构不如他们的干净（他们是独立 backend 类，我们是 hack fa_utils）——重复提交必被拒**

**转向差异化贡献**（查重后价值最大化）：
1. 作者只在 x86 Linux 验证 → **我们补 Apple Silicon 实测数据**
2. 稀疏注意力 CPU 问题**全网没人报** → 我们提 issue

> 💡 教训：**"我修好了" ≠ "该提交"**。先查有没有人在做，再决定：参与 / 验证 / 提 issue / 提 PR。

## 3. gh CLI 认证踩坑全记录（血泪史）

### 3.1 为什么不能用设备码流程

```
设备码流程最后一步：gh POST https://github.com/login/oauth/access_token
→ dial tcp 20.205.243.166:443: i/o timeout
```

- **本机 github.com 被墙**（实测 http=000 超时；api.github.com 却秒通，两者是相邻 IP，被按 IP 过滤）
- 设备码流程**最后一步必须连 github.com** → 无论手机输码多快都失败，这是网络硬伤不是操作问题
- 手机能打开 github.com（不同网络）→ 但 token 交换在本机完成，没用

### 3.2 fine-grained token 权限矩阵（绕晕人的地方）

| 要做的操作 | 需要的权限 |
|---|---|
| 读公开仓库 | 默认即可（Metadata 只读） |
| 发 issue 评论 / PR 评论区 | **Issues: Read and write** |
| 发 PR 评审（review） | **Pull requests: Read and write** |
| push 代码 | **Contents: Read and write** |

**踩过的坑**：
1. 只开了 Contents → `addComment` 报 `Resource not accessible`
2. 加了 Issues → 还是失败（**PR 评论不归 Issues 管**，归 Pull requests！）
3. 加了 Pull requests → 仍然失败！
4. 诊断发现：**"Only select repositories" 只选了 fork，没覆盖上游** → 但用户其实是 "Public repositories" 模式，依然失败
5. 终极诊断：连 octocat/Hello-World 都评论不了 → fine-grained token 实际配置没生效/权限没保存上

### 3.3 最终解法：classic token

```bash
# 简单粗暴，public_repo scope 全覆盖（评论/issue/push fork）
echo 'ghp_xxx' | gh auth login --with-token
# 换 token 报 keyring 错误时先登出：
gh auth logout --hostname github.com   # 需要文件系统权限（~/.config/gh）
gh auth login --with-token
```

**classic token 一步到位**：探针测试直接通过（权限检查过了，只是测试仓库评论超限），正式评论秒发。

> 💡 教训：**fine-grained token 权限组合太绕，做社区互动直接用 classic token（public_repo scope）**。
> 安全上：对话里出现过的 token 用完就删/重建。

## 4. 验证 PR 的方法（无认证也能做）

```bash
# 1. 通过代理拉 PR 分支（不需要 GitHub 认证！）
cd vllm-src
git remote add pr-author https://gh-proxy.com/https://github.com/maobaolong/vllm.git
git fetch pr-author cpu-mla-prefill-backend-fix

# 2. 定位 PR 自己的提交范围（找 fork 点）
git log --oneline --reverse pr-author/cpu-mla-prefill-backend-fix | grep -m3 "CPU.*MLA"

# 3. 看 PR 净改动
git diff <fork点>...<PR头> --stat

# 4. 移植关键文件到本地环境（PR 基于 main，本地是 v0.28.0，需适配）
git show <PR头>:path/to/file > 本地对应路径

# 5. 跑官方测试场景验证
```

**移植时的注意**：PR 基于 main，本地 v0.28.0 有差异（如 main 有 cpu_native.py 占位、selector 结构不同）——要逐文件适配，不能整体替换。验证结果要**诚实声明**：是"移植到 v0.28.0 的验证"，不是完整 main 构建。

## 5. 发布评论 / Issue 的标准动作

```bash
# 发 PR 评论（用 body 文件，方便保留草稿）
gh pr comment 51471 -R vllm-project/vllm --body-file wiki/review_draft_51471.md

# 验证评论已发布
gh api repos/vllm-project/vllm/issues/comments/<id> --jq '{user: .user.login, created: .created_at}'

# 发 issue
gh issue create -R vllm-project/vllm --title "..." --body-file wiki/issue_draft_sparse_attn.md

# 查看 issue / 后续互动
gh issue view 54018 -R vllm-project/vllm
gh pr comment 51471 -R vllm-project/vllm --body "回复..."
```

## 6. 教训总结（下次直接照做）

1. **修好 bug 先查重**：`gh pr list/search` 或 API 搜索，别急着提 PR
2. **差异化贡献**：查重后找"没人做但有价值"的角度——测未覆盖平台、报全新 issue、补文档
3. **评论/issue 草稿存本地**：`wiki/` 里留档，发布前可反复改，发布后可复用
4. **诚实声明验证范围**：移植验证 ≠ 完整构建验证，review 里写清楚
5. **token 用 classic**：`public_repo` scope 一步到位；fine-grained 权限矩阵是坑
6. **安全**：对话中出现的 token 用完即删/重建；gh 存在系统钥匙串（不在 env.sh）
7. **网络现实**：github.com 被墙但 api.github.com 通 → gh 的操作全流程（评论/issue/PR）本机都能做，只有 git push 需要能直连的网络
