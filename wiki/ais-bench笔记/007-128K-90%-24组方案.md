# 007 128K / 90% APC / 24 组的方案

> 需求：**基于 GSM8K 采样，构造 128K 输入、90% APC 命中、24 个公共前缀的数据。**
> 结论：**可以，用 PrefixCache 插件**，四个要求各对应一个配置项。但"90% 能不能到"取决于每组请求数，得先算再 `inspect`。
> 版本基线：`v3.1-20261013-master`。标注：`【文档】`/`【推算】`。

## 1. 参数映射

| 需求 | 配置位置 | 值 |
|---|---|---|
| 基于 GSM8K 采样 | `corpus.path` / `corpus.field` / `corpus.selection.mode` | `./GSM8K.jsonl` / `question` / `random` |
| 128K 输入 | `requests.input_length` | `{"mode":"fixed","value":131072}` |
| 90% APC 命中 | `prefix_cache.target_hit_rate` | `0.9`（token 加权、全局） |
| 24 个公共前缀 | `prefix_cache.groups.count` | `24` |

如果这 24 个前缀在线上流量**不是均分**的，把 `groups.assignment.mode` 换成 `zipf`（`exponent` 控制集中度）或 `weights`（24 个权重显式给）。均匀只是"最干净"的默认。

## 2. 先把 90% 算清楚【推算】

### 2.1 关键事实

每条请求 = `公共前缀 P` + `唯一 seed(16 token)` + `自然文本后缀`。**每个 Group 的第一条请求必然全 miss。**

> ⚠️ **2026-10-28 更正（见 [009](009-实测-1K-90%-24组.md)）**：上一句和下面 §2.2 的 `(n−1)/n` 公式只在 **`cold` 模式**成立。
> `warmup`（本文配置用的就是它）会先在 baseline 前把每个组的前缀灌进缓存，之后**每条请求都命中**，
> 上限变成 `P/L`（本例 1008/1024 = 98.4%）。实测：同样的 48 条，cold 上限 49.2%，warmup 能到 90.0%。
> 所以下面"每组至少 11 条"只适用于 cold；warmup 下每组 2 条就够。

### 2.2 可达上限

```
可达命中率 ≈ (P / 131072) × (n−1)/n          n = 每组请求数
P_max = floor((131072 − 16)/16) × 16 = 131056  （取 block_size=16）
```

| 每组请求数 n | 理论可达上限 | 90% 够不够 |
|---:|---:|:---:|
| 5 | 79.99% | ❌ |
| 10 | 89.99% | ❌（差 0.01 pp） |
| **11** | **90.90%** | ✅ 刚好 |
| 15 | 93.32% | ✅ |
| **20** | **94.99%** | ✅ 舒适 |
| 30 | 96.65% | ✅ |

所以：**24 组 × 11 = 264 条是 90% 的理论最低规模**；24 组 × 10 = 240 条**到不了 90%**（会被 `effective` 压到 89.99%）。

### 2.3 推荐规模

**24 组 × 20 条 = 480 条请求。** 求解器会把每组的 P 定在约 **124,160 token**（`0.9 × 131072 × 20/19 ≈ 124,173`，向下对齐到 16 的倍数），剩余 ~6.9K 是 seed + 自然后缀。

| 量 | 估算 |
|---|---|
| 总输入 token | 480 × 131,072 ≈ **6,290 万** |
| `full.jsonl` + `requests.jsonl` 体积 | 各存一份完整 prompt，合计约 **0.5 GB**（英文 ~4 字符/token 粗估） |
| warmup 请求数 | 24 × `dp_size`（dp=8 → 192 次约 124K token 的 prefill） |
| `prepare` 耗时 | 未实测，按 `O(T)` 估在**分钟级到十几分钟** |

> 如果 480 条太重，退到 **24 × 12 = 288**（上限 91.7%）也够，只是余量小、理论值更依赖精确求解。

## 3. 完整 scenario

已落到 `assets/scenario-128k-apc90-g24.json`，直接复制改路径即可：

```json
{
  "schema_version": "1.0",
  "run": {
    "run_id": "gsm8k-128k-apc90-g24",
    "random_seed": 42,
    "output_dir": "./outputs/gsm8k-128k-apc90-g24"
  },
  "tokenizer": { "path": "/path/to/your/model", "block_size": 16 },
  "corpus": {
    "path": "./GSM8K.jsonl",
    "field": "question",
    "selection": { "mode": "random" }
  },
  "requests": {
    "count": 480,
    "input_length": { "mode": "fixed", "value": 131072 },
    "output_length": { "mode": "fixed", "value": 128 }
  },
  "prefix_cache": {
    "mode": "warmup",
    "target_hit_rate": 0.9,
    "seed_blocks": 1,
    "minimum_non_shared_length": 16,
    "groups": { "count": 24, "assignment": { "mode": "uniform" } },
    "order": { "strategy": "interleave" }
  },
  "service": {
    "inference_url": "http://127.0.0.1:8000/v1/completions",
    "metrics_url": "http://127.0.0.1:8000/metrics",
    "reset_url": "http://127.0.0.1:8000/reset_prefix_cache",
    "model": "your-model-name",
    "dp_size": 8
  },
  "validation": { "target_warning_pp": 1.0, "actual_warning_pp": 8.0 },
  "aisbench": {
    "work_dir": "./outputs/default",
    "extra_args": { "--num-warmups": 0 }
  }
}
```

几个非默认值的理由：

| 字段 | 改法 | 为什么 |
|---|---|---|
| `actual_warning_pp` | 5.0 → **8.0** | 90% 这种高命中率，块对齐+调度+淘汰让实际值天然偏低，5 pp 会天天告警 |
| `output_length` | 512 → **128** | 这个实验测的是 prefill/缓存，decode 越长越浪费机器时间；要测 decode 再调大 |
| `extra_args` | `--num-warmups: 0` | 插件的 Group×DP 预热已经做了，别让 AISBench 再插一脚 |
| `order` | `interleave` | warmup 模式下顺序影响小，交错能让"组间切换"更接近多租户真实形态 |

## 4. 准备语料

插件要的是 **JSONL**（每行含 `question`），而 AISBench 自带的 gsm8k 是 parquet/arrow。用附带的脚本转：

```bash
# 从 HuggingFace 拉
python assets/gsm8k_to_jsonl.py -o GSM8K.jsonl

# 用 AISBench 已经下好的本地目录
python assets/gsm8k_to_jsonl.py -o GSM8K.jsonl --dir ais_bench/datasets/gsm8k
```

产物：

```jsonl
{"question": "Janet’s ducks lay 16 eggs per day...", "answer": "..."}
```

> 语料只需"含 question 字段的 JSONL"，不要求真是 GSM8K。想要更贴近线上的长文档，换成自己的 jsonl + 改 `corpus.field` 即可（但注意 §6 第 2 条）。

## 5. 执行与验收

```bash
pip3 install -e ./plugins/prefix_cache

# ① 规划（不加载 tokenizer、不连服务，秒级）
ais-bench-prefix-cache inspect --scenario ./scenario.json
#    看：target_reachable / reachable_min / reachable_max / effective_target_hit_rate

# ② 造数据（离线，最慢的一步）
ais-bench-prefix-cache prepare --mode text --scenario ./scenario.json
#    看：stdout 最后一行 JSON 里的 manifest/analysis 路径

# ③ 校验产物没被改
ais-bench-prefix-cache validate --manifest <上一步的 manifest 路径>

# ④ 在线压测（需要已开启 prefix caching 的 vLLM）
ais-bench-prefix-cache run --scenario ./scenario.json
```

### `inspect` 输出怎么读

| 字段 | 期望值 | 不对怎么办 |
|---|---|---|
| `target_reachable` | `true` | `false` → 加请求数或降目标 |
| `effective_target_hit_rate` | `0.9` | < 0.9 → 就是 §2 的规模不够 |
| `reachable_max` | > 0.9 | — |
| `groups` | 24 组各 20 条 | 不是 24 → `groups.count` 没生效 |
| `input_tokens.mean` | ≈ 131072 | 偏小 → `tokenizer` 不对或语料太短 |
| `sends_requests` | `false` | — |

### `run` 输出怎么读

终端最后一张两列表：

| 指标 | 期望 |
|---|---|
| 总体目标命中率 | 0.90 |
| 总体理论命中率 | 0.90 ± 1 pp |
| 总体实际命中率 | 0.90 −(1~5) pp 属正常 |
| 理论与实际偏差 | < `actual_warning_pp` |
| 理论与目标偏差 | < `target_warning_pp` |

详细数据在 `result/<run_id>.analysis.json` 的 `theory` / `actual` / `warnings`。

## 6. 开跑前必须确认的六件事

1. **`block_size` 与服务端一致**。vLLM 默认 16，不少部署用 128。不一致 → 理论命中率从错的边界算，整套数据废掉。
2. **`tokenizer.path` 是服务端那个模型的 tokenizer**，不是随便一个同系列的。
3. **服务端 `max_model_len ≥ 131072 + output_length`**，且已开 `--enable-prefix-caching`。
4. **`dp_size` 与线上一致**。它决定 warmup 计划条数和逐 DP 校验；写错会导致预热打偏。
5. **`/reset_prefix_cache` 是否可用**。不可用就设 `assume_empty_cache: true` 并接受"命中率可能偏高"的风险（因为缓存里可能有脏数据）。
6. **这 128K 里约 94% 是构造出来的公共前缀**。GSM8K 只贡献尾部几 K token。它适合压 prefill/缓存，**不代表真实长文档语义**。要语义真实，把 `corpus` 换成真长文本。

## 7. 只要数据、不要压测

`prepare` 是**纯离线**的：不访问服务、不需要 vLLM。产物 `requests.jsonl` 可以直接喂给别的压测工具：

```bash
ais-bench-prefix-cache prepare --mode text --scenario ./scenario.json
# 产物：outputs/gsm8k-128k-apc90-g24_<ts>/result/gsm8k-128k-apc90-g24_<ts>.requests.jsonl
```

此时 `service` 段可以不填（`prepare` 不消费）。但 `manifest.json` 里的 `warmup.plan` 只是**计划**，不预热，别的工具也不认识它——要复现缓存状态，还是得走 `run`。

## 8. 与"朴素方案"的对比

| 方案 | 24 组前缀 | 指定 90% | 理论/实际对账 | 128K 精确长度 |
|---|:---:|:---:|:---:|:---:|
| `synthetic_gen_tokenid` + `PrefixLen` | ❌ 只有 1 个 | ❌ | ❌ | ✅ |
| 自己写 jsonl 手搓 | ✅ | 手工算 | ❌ | ✅ |
| **PrefixCache 插件** | ✅ | ✅ | ✅ | ✅ |

自己手搓的代价：要自己保证 seed 全局唯一、自己按 block 对齐、自己算命中率、自己从 `/metrics` 扒计数器。这些插件都做了。
