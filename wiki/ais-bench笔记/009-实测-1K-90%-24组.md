# 009 实测：1K 输入 / 90% APC / 24 组 × 2 条

> 需求：**基于 GSM8K 采样，构造 1024 token 输入、90% APC 命中、24 个公共前缀、共 48 条（每组 2 条）**。
> 结论：**能做，48 条就够，但必须用 `warmup` 模式**。实测理论命中率 **0.900065**（全局 token 加权，按 16 块对齐），`prepare` 2.6 s，`validate` 通过。
> 同一份配置换成 `cold`，可达上限只有 **0.4922** —— 006 §7.4 / 007 §2.2 的 `(n−1)/n` 公式以"缓存从空开始"为前提，warmup 下不成立。
> 版本：AISBench `7bcb644`（2026-10-26），插件 0.5.0。实测日期 2026-10-28。标注：`【实测】` = 本次容器里跑出来的。

## 4. 结果核对

### 4.1 插件自己的账

| 指标 | 值 |
|---|---|
| 目标命中率 | 0.9 |
| 有效/理论命中率 | **0.900065**（44240 / 49152 token） |
| 目标偏差 | +0.0065 pp（`target_warning_pp=1.0`，无告警） |
| 可达区间 | min 0 / max 0.984375（= 1008/1024） |
| 每条请求前缀 | 29 条 × **928**（58 block）+ 19 条 × **912**（57 block） |
| 组级命中率 | 5 组 = 0.90625（两条都 928），19 组 = 0.8984375（928+912） |
| warmup 计划 | 24 条（= groups × dp_size），每条 944 token，`included_in_formal_statistics=false` |
| warnings | `[]` |

> 为什么不是恰好 0.9：48 × 1024 × 0.9 = 44236.8，命中量必须是 16 的倍数，最近可达是 44240（+3.2 token），
> 也就是 0.900065；`analysis.json` 里 `reason=block alignment prevents an exact target hit count`。

### 4.2 独立复核（不信插件的模拟器）

`assets/1k-apc90-g24/verify.py` 用 tokenizer 重新编码 48 条 prompt，逐项验：

| 检查 | 结果 |
|---|---|
| 条数 / 分组 | 48 条，24 组，每组恰好 2 条 ✅ |
| 实际 token 数 | 48 条全 = **1024**（`set=[1024]`）✅ |
| 组内公共前缀 | 24/24 组的 LCP ≥ 该组最小声明前缀（912 或 928）✅ |
| 24 个前缀互异 | 首 block 两两不同：**24/24** ✅ |
| 独立命中率 | 自算 44240 / 49152 = **0.900065**，与 manifest 逐位一致 ✅ |
| block 对齐 | 所有前缀 % 16 = 0 ✅ |

## 5. 三条结论

### 5.1 「每组 2 条」只有 warmup 能到 90%

【实测】同一份配置把 `mode` 改成 `cold` 再 `inspect`：

```
reachable_max = 0.4921875      # = (1008/1024) × (2−1)/2
effective_target_hit_rate = 0.4921875
target_reachable = false
```

cold 模式下每个 `(group, dp)` lane 从零水位开始，**每组第一条必然全 miss**，所以上限就是
`P_max/L × (n−1)/n = 0.984 × 0.5`。要 90%，1K 下每组得 ≥ **12** 条（`0.984×11/12 = 0.902`），
128K 下是 11 条（007 §2.2，因为 `P_max/L ≈ 1`）。

warmup 模式先在 baseline 之前把 24 个前缀逐组灌进缓存（不进统计），之后 48 条**都命中**。
代价很小：24 条 × 944 token 的预热 prefill，共约 2.3 万 token。

> 换句话说：**006 §7.4 的公式不是"普适规律"，而是 cold 专属**；它假定缓存从空开始，warmup 正好破坏这个前提。
> 本次 48 条的需求能成立，靠的就是这个。

### 5.2 90% 只能给到 0.900065，且组间不均

块对齐把 0.9 抬到 0.900065；求解器按累计输入比例把多出来的命中量摊到 5 个组，
所以组级理论值是 0.90625（5 组）/ 0.8984375（19 组），单条是 0.90625 / 0.890625。
**看总数是 90%，看单组会有 ±0.8 pp 抖动**，验收时别拿单组 0.89 当失败。

### 5.3 1K 里 90% 是「两条 GSM8K 问题循环重复」

| 段 | 928 前缀版 | 912 前缀版 | 内容 |
|---|---:|---:|---|
| 公共前缀 P | 928 | 912 | 该组 2 条问题**循环拼接**（`source_count` 12–27，即重复 6–14 轮） |
| 唯一 seed | 16 | 16 | 1 block 随机 token，全局唯一，防止前缀后误共享 |
| 自然后缀 N | 80 | 96 | **同一组语料池**里取；80/96 token 连一条问题都读不完，所以就是 Q1 开头 |

实际切出来的四段（同一条 prompt）：

```
[前缀 0:40]    Faith's neighborhood, with a total of 20 homes, decided to install ...
[前缀 888:928] ... The sales tax is 5%. Kevin wants to buy six T-shirts, four sweaters, and five jackets ...
[seed 16]      " st st + an l it be if tr }\n al a wh de = with"      ← 唯一的"新信息"
[后缀 80]      Faith's neighborhood, with a total of 20 homes, decided to install ...
```

所以：
- 48 条 prompt 的**新语义只有那 16 个 seed token**，其余全是同一组两条问题的循环；
- 这不是 bug：`_build_group_pools` 给每组的池子大小 = `max(2, 每组请求数)`，本次 48/24 = 2，只有 2 条源文本可循环；
- 压 APC 的**长度 / 块边界 / 命中率**完全没问题（912/928 的边界是精确的）；
- 但不适合语义/精度评测（插件本身也把 `answer` 固定成 `"none"`）；
- 想要更自然的长文：提高 `requests.count`（池子随每组请求数变大，重复度下降），或换 `corpus` 成真长文档（代价是命中率上不去）。

## 7. 上真机前必须对齐的四件事

1. **`block_size`** 与服务端一致（vLLM 默认 16，很多部署 128）。不一致 → 912/928 的边界全错，理论值作废。
2. **`tokenizer.path`** 必须是服务端那个模型的 tokenizer（本次用 Qwen3-0.6B 只是占位）。
3. **`dp_size`** 与服务端一致：它决定 warmup 条数（24×dp）和逐 DP 校验。本次 dp=1。
4. **`/reset_prefix_cache`**：`run` 前要能清缓存，否则 warmup 之外的脏数据会把实际命中率抬高。

`prepare` 本身不需要服务；要拿 **actual** 命中率（`/metrics` 的 `queries`/`hits` 差分）必须跑 `run`。
